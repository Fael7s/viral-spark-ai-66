# ViralCaption

Generates opening hooks, captions, emojis, and hashtags for short-form video posts (TikTok, Instagram Reels, YouTube Shorts) from a text description of the video, gated behind a free/paid daily quota.

## Problem

Creators publishing to TikTok, Reels, and Shorts need platform-specific marketing copy — a hook that holds attention in the first seconds, a caption within that platform's practical length, contextual emojis, and a mix of niche and broad-reach hashtags — for every video, in a specific tone. Writing this by hand for three platforms at once is repetitive and slow. This project turns that into a single form: platform, tone, topic (and optional transcript) in, four structured fields out, generated by an LLM constrained to a fixed JSON schema instead of free text.

## Architecture

The app is a single TanStack Start (React 19) project that serves both the UI and its own backend — there is no separate API service.

- **Routing and rendering**: `@tanstack/react-router` file-based routes under `src/routes` (see `src/routes/README.md` for the convention), rendered server-side by TanStack Start. `src/start.ts` registers global request middleware (Content-Security-Policy and other security headers, a catch-all error handler) and a client-side middleware that attaches the caller's Supabase access token to every server function call. `src/server.ts` wraps the framework's generated server entry to catch cases where the underlying SSR layer (h3) swallows a thrown error into a bare 500 JSON body, and re-renders those as an HTML error page instead.
- **Server functions**: business logic (`generateContent`, `createCheckoutSession`, `createBillingPortalSession`) is implemented as `createServerFn` handlers in `src/lib/*.functions.ts`, called from the client through `useServerFn` like local async functions, but executed only on the server.
- **Auth**: Supabase Auth issues a JWT on sign-in; `src/integrations/supabase/auth-attacher.ts` attaches it as a Bearer token on the client, and `src/integrations/supabase/auth-middleware.ts` (`requireSupabaseAuth`) validates that token on the server, rejecting requests without a well-formed JWT before any handler runs.
- **Data**: Supabase Postgres, accessed two ways. Requests authenticated as the caller use a Supabase client scoped to that caller's JWT, so every query is filtered by the row-level security (RLS) policies defined in `supabase/migrations`. Privileged writes (inserting a generated result, applying a Stripe webhook update) go through a separate service-role client (`src/integrations/supabase/client.server.ts`) that bypasses RLS and is only ever imported inside server-only code.
- **AI generation**: `src/lib/generate.server.ts` calls an external HTTP endpoint, `ai.gateway.lovable.dev`, with the `google/gemini-2.5-flash` model, forcing the response through a single tool call whose arguments are validated against a Zod schema before being used.
- **Billing**: Stripe Checkout (subscription mode) creates the Pro subscription; the Stripe Billing Portal handles self-serve plan management; a webhook route (`src/routes/api/public/stripe-webhook.ts`) keeps the `subscriptions` table in sync with Stripe's view of the subscription.
- **Build/deploy**: Vite 8 with `@lovable.dev/vite-tanstack-config`, which wires in TanStack Start, Tailwind, and Nitro; `vite.config.ts` points the TanStack Start server entry at `src/server.ts` and notes Nitro's default build target is Cloudflare.

## Key implementation details

**Daily quota enforcement is a single atomic Postgres function, not a read-then-write in application code.** `consume_generation` (`supabase/migrations/20260708215650_*.sql`, updated in `20260716233309_*.sql`) reads the caller's plan, upserts today's usage row, locks it with `SELECT ... FOR UPDATE`, and only then compares the count to the limit and increments — all inside one `SECURITY DEFINER` function invoked via `supabase.rpc(...)`. Doing the check-and-increment as two round trips from `src/lib/generate.functions.ts` would let two concurrent requests both read a count under the limit and both proceed, burning more than the daily allowance.

**The `generations` table is insert-locked for regular users; the server does the write.** An early migration granted authenticated users full CRUD via RLS; `supabase/migrations/20260711150916_*.sql` drops that down to `SELECT`-only and revokes the `INSERT`/`UPDATE`/`DELETE` grants outright. `generateContent` (`src/lib/generate.functions.ts`) now writes the row through the service-role client only after `consume_generation` has already validated the caller via `auth.uid()`. A user's own token can no longer insert arbitrary generation rows directly through PostgREST, even if they discover the table name.

**The Stripe webhook treats its three failure points differently on purpose.** `src/routes/api/public/stripe-webhook.ts` checks `processed_webhooks` for the event ID before doing any work (idempotency), and additionally compares `event.created` against `last_stripe_event_created` on the subscription row before applying `subscription.updated`/`.deleted` events (protects against Stripe redelivering events out of order). A failed idempotency lookup or failed subscription write returns `500`, so Stripe retries. But if the subscription write already succeeded and only the final "mark this event processed" insert fails, the handler still returns `200` and just logs — retrying at that point risks re-running an already-applied upgrade, which the code judges as worse than a rare gap in the idempotency table.

**Pro-only tones are re-checked on the server, independent of what the UI shows.** `PRO_ONLY_TONES` (`src/lib/types.ts`) hides two tones behind a lock icon for Free accounts in `src/routes/_authenticated/app.tsx`, but `generateContent` calls `assertTonePermitted` against the caller's actual `subscriptions.plan` before generating anything, and a missing or unrecognized plan value is treated as Free — never as an implicit pass. The UI restriction is cosmetic; the enforcement is the server check, because the server function is callable directly regardless of what the UI renders.

**User-supplied text going into the LLM prompt is treated as untrusted data, not instructions.** `sanitizeUserInput` (`src/lib/generate.server.ts`) strips sequences that look like the delimiter tags used in the prompt (`<input_usuario>`, `<system>`, etc.) before the topic and transcript are wrapped in those tags, and the system prompt explicitly tells the model to treat everything inside them as data to describe, never as commands. The model's reply is also constrained to a single forced tool call rather than free text, and the tool arguments are parsed and validated against a Zod schema (`resultSchema`) before being returned to the client — malformed or off-schema output is rejected as `AI_BAD_OUTPUT` rather than passed through.

## Running locally

Install dependencies:

```
bun install
```

(`npm install` also works — a `package-lock.json` is checked in alongside `bun.lock`.)

Provision a Supabase project and apply the SQL migrations in `supabase/migrations/` in order — the app depends on the tables, RLS policies, and the `consume_generation` / `check_rate_limit` Postgres functions they define.

Copy `.env.example` to `.env` and set:

| Variable | Used by |
| --- | --- |
| `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY` | Server-side Supabase client (`auth-middleware.ts`, `client.ts`) |
| `SUPABASE_SERVICE_ROLE_KEY` | Service-role admin client (`client.server.ts`) — bypasses RLS, server-only |
| `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY` | Browser-side mirrors read via `import.meta.env` (`client.ts`) |
| `LOVABLE_API_KEY` | AI gateway call in `generate.server.ts` — **not listed in `.env.example`**, but required or generation fails with `AI_KEY_MISSING` |
| `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `STRIPE_PRICE_ID_PRO` | Stripe checkout, portal, and webhook handling |
| `APP_ORIGIN` or `ALLOWED_HOSTS` | Origin allowlist for Checkout/Portal redirect URLs (`billing.functions.ts`) |

Start the dev server:

```
bun run dev
```

Build for production:

```
bun run build
```

To exercise the Stripe webhook locally, forward events with the Stripe CLI to `/api/public/stripe-webhook` and set `STRIPE_WEBHOOK_SECRET` to the CLI's signing secret. In production, the endpoint is registered in the Stripe dashboard as `https://viral-spark-ai-66.lovable.app/api/public/stripe-webhook`, listening for `checkout.session.completed`, `customer.subscription.updated`, `customer.subscription.deleted`, and `invoice.payment_failed`.

## Testing

```
bun run test       # vitest run
bun run test:ui    # vitest --ui
```

Vitest runs in a `jsdom` environment (`vitest.config.ts`, setup in `src/tests/setup.ts`). All Supabase and Stripe calls in the suite are mocked with `vi.mock` — no test hits a real Postgres instance or the Stripe API, so the RLS policies and the SQL functions themselves are not exercised by this suite, only by manual/DB-level verification.

What's covered, by file:

- `generate.server.test.ts` — AI output schema validation, per-platform prompt content, and the error mapping for gateway failures (rate limit, out of credits, bad output, timeout, missing key)
- `tone-plan-gate.test.ts` — server-side Pro-tone gating (`assertTonePermitted`)
- `limits-and-types.test.ts` — daily limit constants and the platform/tone catalogs
- `billing.test.ts` — Stripe client construction, checkout session metadata, missing-config errors
- `webhook.test.ts` / `webhook-isolated.test.ts` — signature verification, idempotency, and the per-failure-point HTTP status contract described above
- `db.test.ts` — usage/quota reads, favorites, keyset-paginated history
- `integration-flow.test.ts` — generation, billing, and webhook flows chained together (still against mocks)
- `ui-client.test.tsx` — result rendering and the copy/regenerate interactions in the generation UI

Lint: `bun run lint` (ESLint + `typescript-eslint`). Format: `bun run format` (Prettier).

## Known limitations

- The Stripe webhook's per-IP rate limiter (`src/routes/api/public/stripe-webhook.ts`) is an in-memory `Map`. It only limits requests within a single running instance and resets on restart or redeploy — it is not a distributed rate limit.
- `LOVABLE_API_KEY`, required for AI generation, is missing from `.env.example`.
- AI generation depends on one external gateway (`ai.gateway.lovable.dev`) and one hardcoded model (`google/gemini-2.5-flash`); there is no fallback provider or model, and a gateway outage surfaces as a generic error to the user.
- `invoice.payment_failed` sets the subscription `status` to `past_due` but does not itself change `plan`. Since access is gated on `plan` alone, a failed payment does not immediately remove Pro access — this is called out as a deliberate, unresolved product decision in the webhook handler's comments, not an oversight.
- The product UI, generated content, and validation/error messages are all in Brazilian Portuguese (`<html lang="pt-BR">` in `src/routes/__root.tsx`); there is no internationalization layer.
- The test suite mocks Supabase and Stripe entirely; RLS policies and the Postgres functions in `supabase/migrations` have no automated coverage in this repository.
